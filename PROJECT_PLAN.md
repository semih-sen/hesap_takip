## 1. Product Summary

A fully offline, local-first personal income/expense ledger with:

- **Accounts → Wallets** hierarchy (an Account groups one or more Wallets; each Wallet has its own currency and balance).
- **Multi-currency** support with **per-transaction exchange-rate snapshots**.
- **Transactions ↔ Categories** many-to-many (a transaction can carry multiple categories, with optional per-category split amounts).
- **Partial Payments**: a *pending parent* (a bill/debt/receivable) settled by one or more *completed child* payments.
- **Transfers** between wallets (including cross-currency).
- **Recurring transactions** generated by a rules engine.
- A **Summary section** and a **Transaction List** that use **independent, decoupled filtering scopes**.
- **Strict Material 3 Dark Theme only** (no light theme is written anywhere).

**Target toolchain:** Flutter `3.44.4` (installed). Dart from that SDK. Pin exact package versions during Phase 0.

## 2. Non-Negotiable Constraints (read before every phase)

1. **Money is never a `double`.** All monetary amounts are stored and computed as **integer minor units** (`amountMinor`). Currency decimal places are currency-aware (TRY=2, USD=2, JPY=0, BHD=3). Use the `decimal` package only for rate arithmetic, then convert to integer minor units for storage.
2. **Exchange rate is snapshotted on the transaction** at creation time. Reports read the stored `baseAmountMinor`; they **never** recompute historical amounts with a live rate.
3. **Dark theme only.** Do not author a `ThemeData.light()` or any light `ColorScheme`. `MaterialApp.themeMode = ThemeMode.dark` and only `darkTheme` is provided.
4. **The transaction list row is a bespoke widget** (`TransactionListItem`) with a 3-row layout, a vertical color stripe, and a transparent/tinted background. **Do not** substitute a generic `ListTile`.
5. **Summary scope ≠ List scope.** These are two separate Riverpod states. Changing one must never mutate the other.
6. **Pending parent transactions do not move money.** Only `completed` transactions affect wallet balances. This prevents double-counting of partial payments.
7. **Atomicity.** Partial payments, transfers, and recurring generation each run inside a single Drift transaction (`db.transaction { ... }`).
8. **Modularity.** Strictly separate `presentation` / `application` (state) / `data` layers. UI never touches the database directly; it goes through providers → repositories → DAOs.

## 5. Data Model (Drift Schema — schema version 1)

> These table definitions are **canonical**. Implement them verbatim in Phase 1. Money columns end in `Minor`. All enums are stored via `intEnum<T>()`.

### 5.1 Enums

```dart
enum AccountType { bank, cash, creditCard, person, investment, other }
enum CategoryType { income, expense }
enum TransactionType { income, expense, transfer }
enum FlowDirection { inflow, outflow }        // decouples money sign from semantic type
enum TransactionStatus { completed, pending, scheduled, cancelled }
enum RecurrenceFrequency { daily, weekly, monthly, yearly }
```

**Design note (`FlowDirection`):** Every transaction stores a `flowDirection`. `type` describes *what* it is (income/expense/transfer); `flowDirection` describes *which way money moves* (inflow/outflow). This makes balance math trivial and unambiguous, and cleanly handles the two legs of a transfer:

- income → inflow, expense → outflow
- transfer **out** leg → outflow, transfer **in** leg → inflow

## 6. Money & Currency Handling (core, implement in Phase 2)

**`Currency` metadata** (static registry): `code`, `symbol`, `minorDigits`, `symbolOnLeft`. Seed at least TRY, USD, EUR, GBP; make it extensible.

**`CurrencyService` responsibilities:**
- `int toMinor(Decimal amount, String code)` — scales by `10^minorDigits`, rounds **half-up**, returns integer.
- `Decimal fromMinor(int minor, String code)` — inverse.
- `String format(int minor, String code, {Locale locale})` — uses `NumberFormat.currency` with `tr_TR` grouping; symbol per currency metadata.
- `int convertMinor({required int amountMinor, required String fromCode, required String toCode, required Decimal rate})` — converts across currencies at a given rate, half-up rounding, returns integer minor units in `toCode`.

**Rounding policy:** half-up, applied once at the boundary of any conversion. Never chain float rounding. Document any residual (e.g., splitting a bill across categories: last allocation absorbs the rounding remainder so allocations always sum to the total).

**Rate snapshot algorithm (every transaction):**
1. User enters `amount` in the wallet currency (`currencyCode`).
2. Resolve `exchangeRateToBase` = rate from `currencyCode` → `AppSettings.baseCurrencyCode`. If same currency, rate = `1`. Prefill from `ExchangeRates` cache (latest ≤ valueDate) but allow manual override.
3. `baseAmountMinor = convertMinor(amountMinor, currencyCode, baseCurrency, rate)`.
4. Persist `amountMinor`, `currencyCode`, `exchangeRateToBase`, `baseAmountMinor` together.

**Proactive edge cases (must be handled, not ignored):**
- Changing the app base currency later **must not** rewrite historical `baseAmountMinor`. Old rows stay as recorded (already correct at their time). Only new transactions use the new base. Surface this clearly in Settings.
- Cross-currency transfer and cross-currency partial payment each need their own rate; see §8.3 and §8.2.

## 7. Date Handling

- `valueDate` is a **date-only** concept. Store it as a `DateTime` normalized to **local midnight** (`DateTime(y, m, d)`), and only ever compare/group by its date part. Never store `DateTime.now()` (with time) into `valueDate`.
- Provide `AppDate.today()`, `AppDate.dateOnly(dt)`, and `AppDate.addMonthsClamped(dt, n)` (see §8.4) in `core/date/app_date.dart`.
- Reporting/grouping uses `valueDate`; auditing uses `createdAt`/`updatedAt` (full timestamps).

## 8. Business Logic Services

### 8.1 `BalanceService`

```
walletBalanceMinor(walletId):
  return initialBalanceMinor(walletId)
       + Σ amountMinor WHERE walletId = ? AND status = completed AND flowDirection = inflow
       - Σ amountMinor WHERE walletId = ? AND status = completed AND flowDirection = outflow
```

- Pending/scheduled/cancelled transactions are excluded. Parent bills (pending) therefore never touch balance.
- Expose reactive `Stream<int>` per wallet and an aggregated stream for a set of wallets.

### 8.2 `PartialPaymentService` (implement in Phase 9)

**Model recap:** A *parent* is a `pending` transaction representing a bill/debt/receivable. It carries `plannedAmountMinor` and cached `settledAmountMinor`. It **does not move money**. Each *child* is a `completed` transaction (real money movement) with `parentTransactionId` set. When `settledAmountMinor >= plannedAmountMinor`, the parent flips to `completed`.

**`applyPayment` (atomic):**
```
applyPayment({parentId, sourceWalletId, paymentAmountMinor, paymentCurrency,
              rateToParentCurrency, rateToBase, valueDate, note, allowOverpayment=false}):
  db.transaction {
    parent = load(parentId); assert(parent.status == pending)
    remaining = parent.plannedAmountMinor - parent.settledAmountMinor
    paymentInParent = convertMinor(paymentAmountMinor, paymentCurrency,
                                   parent.currencyCode, rateToParentCurrency)
    if (paymentInParent > remaining && !allowOverpayment):
        throw OverpaymentFailure(remaining, paymentInParent)   // default: reject, ask user to adjust
    child = insert Transactions(
        walletId: sourceWalletId, type: parent.type,
        flowDirection: parent.flowDirection, status: completed,
        amountMinor: paymentAmountMinor, currencyCode: paymentCurrency,
        exchangeRateToBase: rateToBase,
        baseAmountMinor: convertMinor(paymentAmountMinor, paymentCurrency, baseCurrency, rateToBase),
        valueDate: valueDate, note: note, parentTransactionId: parent.id)
    newSettled = parent.settledAmountMinor + paymentInParent
    update parent set settledAmountMinor = newSettled,
                      status = (newSettled >= parent.plannedAmountMinor ? completed : pending),
                      updatedAt = now
  }
```

**`reversePayment(childId)` (atomic):**
```
db.transaction {
  child = load(childId); parent = load(child.parentTransactionId)
  paymentInParent = convertMinor(child.amountMinor, child.currencyCode,
                                 parent.currencyCode, rateUsedForChild)
  update parent set settledAmountMinor = settled - paymentInParent,
                    status = pending, updatedAt = now
  delete child
}
```

**Edge cases (all mandatory):**
- **Overpayment:** default reject with a typed failure; the UI must let the user cap the amount to `remaining` or explicitly opt into overpayment.
- **Cross-currency payment:** child stored in its own wallet currency; `paymentInParent` uses `rateToParentCurrency`; `baseAmountMinor` uses `rateToBase`. Two independent rates — both snapshotted.
- **Deleting a parent that has children:** block by default (`ParentHasChildrenFailure`); require explicit "delete bill and all its payments" confirmation, which cascade-deletes children inside one transaction and reverses their balance effects implicitly (children are removed → balance recomputes).
- **Rounding:** integer minor units throughout; the settled/remaining comparison is exact.
- **Data-integrity repair:** provide `recomputeSettled(parentId)` that recomputes `settledAmountMinor` from children as a self-heal utility (used by tests and a hidden maintenance action).

### 8.3 `TransferService` (Phase 8)

```
createTransfer({fromWalletId, toWalletId, fromAmountMinor, toAmountMinor,
                rate, valueDate, note}):
  groupId = uuid()
  db.transaction {
    insert out-leg: walletId=fromWalletId, type=transfer, flowDirection=outflow,
                    status=completed, amountMinor=fromAmountMinor,
                    currencyCode=fromWallet.currency, transferGroupId=groupId,
                    exchangeRateToBase/baseAmountMinor = snapshot(fromWallet.currency)
    insert in-leg:  walletId=toWalletId,   type=transfer, flowDirection=inflow,
                    status=completed, amountMinor=toAmountMinor,
                    currencyCode=toWallet.currency, transferGroupId=groupId,
                    exchangeRateToBase/baseAmountMinor = snapshot(toWallet.currency)
  }
```

- **Cross-currency:** `fromAmountMinor` and `toAmountMinor` differ; store the `rate` used. Same-currency transfer: amounts equal, rate = 1.
- **Edit/delete:** always operate on **both legs** by `transferGroupId`, atomically.
- **Summary treatment:** transfers are **excluded** from income/expense totals (they net to zero across the user's own wallets) but they **do** affect per-wallet balances. Document and enforce in `SummaryService`.

### 8.4 `RecurringService` (Phase 10)

**Entry point:** `generateDueEntries(DateTime now)` — called on app startup (via a provider) and available as a manual "generate now" action.

```
for each rule in activeRules:
  anchor = rule.lastGeneratedDate ?? dayBefore(rule.startDate)
  while true:
    next = nextOccurrenceAfter(anchor, rule)          // respects frequency, interval, byMonthDay/byWeekday
    if next == null: break
    if next > AppDate.dateOnly(now): break             // do not generate the future beyond today (configurable horizon)
    if rule.endDate != null && next > rule.endDate: break
    if rule.maxOccurrences != null && rule.generatedCount >= rule.maxOccurrences: break
    db.transaction {
      // idempotency: UNIQUE(recurringRuleId, valueDate) guard; skip if exists
      insert Transactions(
        walletId: rule.walletId, type: rule.type, flowDirection: rule.flowDirection,
        status: rule.autoPost ? completed : pending,
        amountMinor: rule.amountMinor, currencyCode: rule.currencyCode,
        exchangeRateToBase/baseAmountMinor: snapshot(rule.currencyCode, at: next),
        valueDate: next, recurringRuleId: rule.id,
        // If not autoPost, insert a PLAIN pending row (status: pending set
        // explicitly) — settle-in-place (Phase 9 rework), so NO
        // plannedAmountMinor/settledAmountMinor. It is immediately usable by the
        // existing swipe-to-settle flow. The explicit status override matters:
        // generation only ever produces on-or-before-today dates, so without it
        // a date-derived status would wrongly classify the row as completed.)
      insert rule categories into TransactionCategories
      update rule set lastGeneratedDate = next, generatedCount = generatedCount + 1
    }
    anchor = next
```

**`addMonthsClamped(date, n)` and month-day clamping (critical):**
- Adding months to Jan 31 must yield Feb 28 (or 29 in a leap year), Apr 30, etc. Implement by computing the target year/month, then `day = min(rule.byMonthDay ?? date.day, lastDayOfMonth(year, month))`.
- This clamping must not "drift": always derive the next date from the rule's `byMonthDay`/`startDate` day, not from the previously clamped day (so a Jan 31 monthly rule stays on the 31st in months that have it).

**Series editing semantics (UI + service):**
- **This occurrence only:** detach the single generated transaction from the rule (`recurringRuleId = null`) and edit it.
- **This and future:** end the current rule at the edited date (`endDate = date - 1`) and create a new rule with the new parameters starting at `date`.
- Never silently rewrite already-generated past transactions.

**Idempotency:** the `UNIQUE(recurringRuleId, valueDate)` index guarantees re-running `generateDueEntries` cannot create duplicates. Handle the unique-constraint conflict by skipping.

### 8.5 `UndoService` (Phase 2 & 12)

**Concept:** To prevent complex cascading data loss (e.g., deleting a parent transaction with partial payments) and to align with Material 3 guidelines, "Undo" is handled via **Delayed Execution (Command Pattern)** in the application layer, rather than soft-deletes in the database.

**Mechanism:**
1. When a user deletes or mutates a critical record (Transaction, Category, Wallet), the UI calls `UndoService.queueAction(...)`.
2. The service holds the action (a closure or a Command object) in a Riverpod state (`PendingActionQueue`).
3. The UI optimistically updates or removes the item from the local Riverpod provider (so it disappears from the screen instantly).
4. A Material 3 `SnackBar` is shown with an "Undo" (Geri Al) button and a 4-5 second timer.
5. If the timer expires, `UndoService` executes the actual Drift transaction (`db.transaction { ... }`).
6. If the user taps "Undo", the action is discarded from the queue, and the optimistic Riverpod state is reverted (the item reappears).

**Safety Net:** 
If the app is closed while an action is pending in the queue, `WidgetsBindingObserver` (or a Riverpod `onDispose` hook) must immediately commit all pending actions to Drift before the isolate dies.

## 9. State Management (Riverpod) — the two-scope rule

**Repositories** are exposed as keep-alive providers; notifiers depend on them. The **two independent scopes** are the heart of the app:

```dart
// ---- SUMMARY SCOPE (dashboard summary card) ----
// Holds the set of wallet ids the summary aggregates over. Empty set = ALL wallets.
@riverpod
class SummaryWalletSelection extends _$SummaryWalletSelection {
  @override
  Set<int> build() => <int>{};                 // default: all
  void toggle(int walletId) { /* add/remove */ }
  void selectAll() => state = <int>{};
  void setSelection(Set<int> ids) => state = ids;
}

@riverpod
Stream<SummaryData> summary(SummaryRef ref, DateRange period) {
  final selection = ref.watch(summaryWalletSelectionProvider);
  final repo = ref.watch(transactionRepositoryProvider);
  return repo.watchSummary(walletIds: selection, period: period); // base-currency totals
}

// ---- LIST SCOPE (transaction list) — completely independent ----
@riverpod
class TransactionListFilter extends _$TransactionListFilter {
  @override
  TransactionFilter build() => TransactionFilter.initial(); // accounts = ALL by default
  void setDateRange(DateRange r);
  void setWallets(Set<int> ids);       // independent from SummaryWalletSelection
  void setCategories(Set<int> ids);
  void setType(TransactionType? t);
  void setStatus(TransactionStatus? s);
  void setSearch(String q);
  void reset();
}

@riverpod
Stream<List<TransactionListRow>> transactionList(TransactionListRef ref) {
  final filter = ref.watch(transactionListFilterProvider);
  final repo = ref.watch(transactionRepositoryProvider);
  return repo.watchTransactions(filter); // all wallets unless filter narrows them
}
```

**Enforced invariant:** `SummaryWalletSelection` and `TransactionListFilter.wallets` are separate providers. A change to the summary account selection must not read from or write to the list filter, and vice-versa. Add a widget test asserting this decoupling.

Other providers: `appDatabaseProvider` (keepAlive), `settingsProvider`, `accountRepositoryProvider`, `walletRepositoryProvider`, `categoryRepositoryProvider`, `recurringRepositoryProvider`, `currencyServiceProvider`, plus form notifiers (`TransactionFormController`, etc.). Use `AsyncNotifier`/`StreamProvider` to bridge Drift's reactive queries.

### 10.3 `TransactionListItem` — the bespoke row (canonical spec)

**Layout contract (implement exactly; no `ListTile`):**
- Root is a `RepaintBoundary` wrapping a fixed-radius container.
- **Left vertical color stripe:** width ~5px, full item height, rounded left corners, color = the **owning account's** color (`Wallet.accountId → Account.colorValue`) — it communicates *which account/wallet* the money belongs to. This is sourced independently of the tint below (Part A refactor): the stripe reads `accountColorValue`, the tint reads `accentColorValue`.
- **Body background:** the **category/type accent** (`accentColorValue` = primary category color, else income/expense/transfer accent) at low opacity (`accent.withValues(alpha: 0.08–0.12)`) — a *transparent tint*, never a solid fill. Unchanged by the stripe refactor.
- **Uniform height:** the Row-3 slot is rendered unconditionally at a fixed height (even when empty), so every variant (completed, pending, transfer, recurring, or bare) renders at the exact same height.
- **Three rows** in a `Column`:
  - **Row 1:** `Expanded` title (primary category or payee, `titleMedium`, ellipsis) on the left; **amount** on the right, colored by flow (income = income accent, expense = expense accent, transfer = transfer accent), bold, currency-formatted for the transaction's currency.
  - **Row 2:** wallet name + optional note/payee (muted `bodySmall`) on the left; formatted `valueDate` (`tr_TR`) on the right.
  - **Row 3 (contextual):**
    - Pending parent with partial payments → a slim `LinearProgressIndicator` (settled/planned) + label like "Kısmen ödendi: {settled}/{planned}".
    - Recurring-generated → a "Tekrarlayan" chip.
    - Transfer → "Transfer → {counterWallet}".
    - Otherwise → up to N category chips.
- Constructor takes a single immutable view-model (`TransactionListRow`) and is `const`-friendly; use `ValueKey(row.id)`. No provider reads inside the item — it is a pure presentational widget for maximum list performance.

> Phase 6 delivers the fully written widget. It lives at `features/transactions/presentation/widgets/transaction_list_item.dart` and is covered by a golden test.

## 12. Key Invariants & Edge-Case Checklist (verify continuously)

- [ ] No `double` anywhere in money paths; all `amountMinor` integers.
- [ ] `baseAmountMinor` + `exchangeRateToBase` snapshotted at write; never recomputed for history.
- [ ] Pending parents excluded from wallet balances; only `completed` rows count.
- [ ] Partial payment updates parent `settledAmountMinor` + status atomically; reversal restores parent.
- [ ] Overpayment rejected by default with a clear, adjustable path.
- [ ] Cross-currency partial payment carries two snapshotted rates (to-parent, to-base).
- [ ] Transfers are two atomic legs; excluded from income/expense summary; included in balances.
- [ ] Recurring generation is idempotent (`UNIQUE(recurringRuleId, valueDate)`).
- [ ] Month-end recurrence clamps and does not drift.
- [ ] Summary scope and List scope are separate Riverpod states (asserted by test).
- [ ] `valueDate` is date-only; grouping/reports never suffer timezone drift.
- [ ] Deleting a wallet/account with transactions is blocked or archived, never orphaning ledger rows.
- [ ] All user-facing strings come from ARB (Turkish); code stays English.
